🔒 IAM & Security

🔑 Core IAM Concepts

  • Users = individuals, Groups = collection of users (no nesting), Roles = temp credentials for services/cross-account, Policies = JSON permission docs
  • Root account: never use daily. Enable MFA immediately. Only for account-level tasks
  • Identity-based policies: attached to user/group/role — Resource-based policies: attached to resource (e.g. S3 bucket policy)
  • Instance Profile = wrapper around IAM Role for EC2 to assume it. Never store credentials on EC2
  • Permission Boundary: sets maximum permissions an entity can have. Does NOT grant permissions
  • Trust Policy: defines who (principal) can assume a role

🔑 STS & Cross-Account

  • STS AssumeRole: returns temp credentials. Duration: 1 hr default, up to 12 hrs
  • Cross-account: Account B creates role with trust policy for Account A → Account A user calls AssumeRole
  • Resource-based policy (S3 bucket policy) doesn't require giving up your own permissions unlike AssumeRole

🔑 IAM Conditions

  • aws:SourceIp, aws:RequestedRegion, aws:MultiFactorAuthPresent, aws:PrincipalOrgID
  • IAM Access Analyzer: identifies resources shared with external entities (outside org)

🔑 Cognito & Federation

  • Cognito User Pools = authentication (sign-up/sign-in, JWT) — "who are you?"
  • Cognito Identity Pools = authorization (temp AWS credentials via STS) — "what can you access?"
  • SAML 2.0: enterprise SSO (ADFS) | IAM Identity Center (SSO): multi-account SSO

🔑 Security Services

  • WAF: Layer 7 on ALB/CloudFront/API GW. Rules: IP sets, geo match, rate limiting, SQL/XSS protection
  • Shield Standard: free, auto DDoS protection | Shield Advanced: $3,000/month, DDoS Response Team
  • GuardDuty: ML threat detection from VPC Flow Logs, CloudTrail, DNS. No agents needed

⚠️ Exam Tips & Gotchas

  • "FIPS 140-2 Level 3" → always CloudHSM
  • "Auto-rotate DB credentials" → Secrets Manager
  • "Encrypt large data with KMS" → Envelope encryption (GenerateDataKey, NOT Encrypt API — 4KB limit)
  • "Restrict all accounts from a region" → SCP + aws:RequestedRegion deny
  • Management account is NEVER affected by SCPs
  • "SSL cert for CloudFront" → must be in us-east-1
  • "Temp AWS creds for mobile users" → Cognito Identity Pools
  • GuardDuty=detection | Inspector=vulnerability scanning | Detective=investigation

🔑 Placement Groups & Hibernate

  • Cluster: same rack, lowest latency/highest throughput. Risk: single rack failure
  • Spread: different hardware per instance. Max 7 instances per AZ
  • Partition: up to 7 partitions per AZ, hundreds of instances. For Hadoop/Kafka/Cassandra
  • Hibernate: RAM saved to encrypted EBS root. Max 60 days. Enabled at launch. RAM <150GB
  • io1/io2 Multi-Attach: up to 16 Nitro instances in the same AZ
  • Instance Store: physically attached, best I/O, data lost on stop/terminate/hardware failure

⚠️ Exam Tips & Gotchas

  • "Highest disk I/O" → Instance Store (ephemeral!)
  • "100GB gp2 poor IOPS" → only 300 IOPS. Switch to gp3 (baseline 3,000)
  • st1 and sc1 CANNOT be boot volumes
  • "Move EBS to another AZ" → snapshot → create volume in new AZ
  • "Licensing tied to physical cores" → Dedicated Host
  • "Fault-tolerant batch processing cheaply" → Spot
  • If AWS interrupts Spot: no charge for partial hour. If YOU terminate: charged
  • "Shared file system for Linux" → EFS | "For Windows" → FSx for Windows

🔑 RDS Proxy

  • Fully managed serverless proxy. Reduces failover time by 66%
  • Ideal for Lambda (pools short-lived connections to prevent DB exhaustion)
  • Enforces IAM auth. Must be in VPC — not publicly accessible

🔑 Aurora Deep Dive

  • MySQL/PostgreSQL compatible. Storage auto-grows 10GB increments to 128TB
  • 6 copies across 3 AZs: 4/6 needed for writes, 3/6 for reads. Self-healing storage
  • Writer endpoint + Reader endpoint (load balanced across up to 15 read replicas)
  • Aurora Global: 1 primary + up to 5 secondary regions. Lag <1 sec. RTO <1 min
  • Aurora Serverless v2: auto-scales 0.5 ACU steps. For unpredictable workloads
  • Aurora Multi-Master: every node can write. Zero downtime for writes

📨 SQS, SNS & Kinesis

🔑 SQS Key Facts

  • Standard: unlimited throughput, at-least-once, best-effort ordering
  • FIFO: 300 msg/sec (3,000 with batching), exactly-once, strict ordering
  • Max message size: 256KB. Retention: 1 min–14 days (default 4 days)
  • Visibility timeout: 0-12 hrs (default 30s). Use ChangeMessageVisibility to extend
  • Long Polling: wait up to 20s. Preferred — reduces empty API calls and cost
  • DLQ: messages after MaxReceiveCount go here. FIFO queue DLQ must also be FIFO

🔑 SNS Key Facts

  • Push-based pub/sub. Subscribers: SQS, Lambda, HTTP/HTTPS, Email, SMS, Kinesis Firehose
  • Fan-out pattern: SNS → multiple SQS queues (fully decoupled, no data loss)
  • Message filtering: JSON filter policy per subscription
  • FIFO topics: only SQS FIFO queues can subscribe

🔑 Kinesis

  • KDS: real-time. Retention 1-365 days. Replayable. Per shard: 1MB/s write, 2MB/s read
  • Enhanced Fan-Out: 2MB/s per consumer per shard (push via HTTP/2)
  • Firehose: loads to S3/Redshift/OpenSearch. Near real-time (60s buffer). NO replay
  • Hot partition = poorly distributed partition keys

  • "Decouple + one consumer" → SQS
  • "Fan-out to multiple subscribers" → SNS + SQS fan-out

🐳 ECS, Fargate & EKS

🔑 Core Concepts

  • ECS = AWS-managed container orchestration service; runs Docker containers as Tasks grouped into Services
  • Two launch types: EC2 and Fargate
  • EC2 Launch Type: you provision & manage EC2 instances, must install ECS Agent (pre-installed on ECS-optimized AMI), you control instance type/capacity
  • Fargate Launch Type: serverless — no EC2 to manage, AWS provisions infra, you define CPU/memory at task level
  • Task Definition: JSON blueprint — image, CPU, memory, port mappings, env vars, IAM task role, logging config
  • ECS Service: maintains a desired count of running tasks, handles replacement of failed tasks
  • Load Balancer integration: ALB (preferred, supports path-based routing, dynamic port mapping), NLB (high throughput/low latency, TCP/UDP), Classic LB (not recommended, no dynamic port mapping)
  • Dynamic Port Mapping: ALB can route to multiple tasks on the same EC2 instance using different ports
  • Service Auto Scaling: target tracking (e.g., avg CPU 70%), step scaling, scheduled scaling — scales tasks, NOT EC2 instances
  • Cluster Auto Scaling: uses Capacity Providers to scale underlying EC2 instances (EC2 launch type only)
  • Capacity Provider tied to an ASG — ECS tells ASG to add/remove instances based on task placement needs

🔐 IAM Roles

  • EC2 Instance Profile: used by the ECS Agent on EC2 instances to call ECS API, pull images from ECR, send logs to CloudWatch — applies to EC2 launch type only
  • ECS Task Role: assigned per task definition, grants the container permissions to access AWS services (S3, DynamoDB, etc.)
  • Best practice: use least privilege task roles — each service gets its own task role with only required permissions
  • Exam Trap: Instance Profile ≠ Task Role. If a question asks about granting a specific container access to S3, the answer is Task Role, NOT instance profile

📦 Storage & Data

  • EFS can be mounted onto ECS tasks — works with both EC2 and Fargate launch types
  • EFS + Fargate = serverless + shared persistent storage (great combo for multi-AZ)
  • Exam Trap: S3 cannot be mounted as a filesystem on ECS tasks — if question says "mount S3", it's wrong
  • Ephemeral storage on Fargate: default 20 GB, configurable up to 200 GB (shared among containers in same task)
  • Bind mounts: share data between containers in the same task

🖼️ ECR (Elastic Container Registry)

  • Stores, manages, and deploys Docker container images
  • Private repositories (IAM-controlled access) or Public (ECR Public Gallery at gallery.ecr.aws)
  • Supports image vulnerability scanning, lifecycle policies to clean old images
  • Cross-region and cross-account replication supported
  • Images encrypted at rest with KMS

☸️ EKS (Elastic Kubernetes Service)

  • Managed Kubernetes — AWS manages the control plane (API server, etcd)
  • Use case: company already running K8s on-prem or elsewhere → migrate to EKS
  • Node types:
    • Managed Node Groups: AWS provisions & manages EC2 nodes, auto-scaling
    • Self-Managed Nodes: you create & register EC2 instances, more control
    • Fargate: serverless pods, no nodes to manage
  • EKS Anywhere: run EKS on your own on-premises infrastructure
  • EKS Distro: run the same K8s distribution used by EKS anywhere, self-managed
  • EKS supports CloudWatch Container Insights for monitoring

🚀 App Runner

  • Fully managed service to deploy web apps and APIs at scale — no infrastructure knowledge needed
  • Input: container image (ECR) or source code (GitHub)
  • Auto-scales, load balancing, encryption, health checks, VPC access — all managed
  • Use case: developers who want to deploy quickly without learning ECS/EKS/Fargate

⚠️ Gotchas & Exam Tips

  • Key "Serverless containers" = Fargate
  • Key "Migrate existing Kubernetes" = EKS
  • Key "No infra knowledge, just deploy code" = App Runner
  • Trap Service Auto Scaling scales tasks. Cluster Auto Scaling (Capacity Providers) scales EC2 instances. Don't confuse them.
  • Trap EC2 Instance Profile is NOT used in Fargate — Fargate uses only Task Execution Role (to pull images, push logs) + Task Role (app permissions)
  • Trap ECS placement strategies (spread, binpack, random) only apply to EC2 launch type, NOT Fargate
  • Trap If the question mentions persistent shared storage across tasks → EFS (not EBS, not S3)
  • Trap ALB is preferred over NLB for ECS unless the question specifically mentions high throughput, TCP, or static IP requirements
  • Trap EKS cluster costs $0.10/hr (~$72/month) for the control plane alone, plus compute costs
  • Remember Fargate task sizes: 0.25–16 vCPU, 0.5–120 GB memory (specific valid combinations)
  • Remember ECS on EC2: binpack = cost optimize (fill instances), spread = HA (distribute across AZs)

⚡ Lambda & Serverless

🔑 Core Concepts

  • Lambda: event-driven, serverless compute — pay per invocation + duration
  • Max execution time: 15 minutes (900 seconds)
  • Memory: 128 MB to 10,240 MB (10 GB) in 1 MB increments
  • CPU scales proportionally with memory (at 1,769 MB you get 1 full vCPU)
  • /tmp storage: 512 MB to 10,240 MB (10 GB)
  • Deployment package: 50 MB zipped, 250 MB unzipped (including layers)
  • Environment variable size: 4 KB total
  • Default concurrency: 1,000 per region (soft limit, can request increase)
  • Burst concurrency: varies by region (e.g., 3,000 in us-east-1, 1,000 in most others, 500 in some)
  • Supports: Node.js, Python, Java, .NET, Go, Ruby, custom runtimes via Lambda Runtime API

🎯 Triggers & Invocation Models

  • Synchronous: API Gateway, ALB, CloudFront, Cognito — caller waits for response
  • Asynchronous: S3, SNS, EventBridge, CloudWatch Events, SES, CodeCommit, CodePipeline — Lambda retries twice on failure, then sends to DLQ (SQS/SNS) or Destination
  • Event Source Mapping: Kinesis, DynamoDB Streams, SQS — Lambda polls the source, processes in batches
  • Destinations (async only): route success/failure to SQS, SNS, Lambda, or EventBridge — preferred over DLQ (provides more context: request payload, response, etc.)

🔄 Concurrency & Cold Starts

  • Cold start = download code → start runtime → run init code → execute handler
  • Reserved Concurrency: caps a function's max concurrency — guarantees capacity for that function, but also limits it. Protects other functions from being starved
  • Provisioned Concurrency: pre-warms N instances — eliminates cold starts. Costs money even when idle. Use with Application Auto Scaling to schedule.
  • Unreserved concurrency: shared pool for all functions without reserved concurrency
  • If total concurrency exceeds limit → throttling (synchronous: 429 error, async: retries then DLQ)

🔒 Lambda & VPC

  • Lambda NOT in VPC: has internet access by default, can call public APIs and AWS services
  • Lambda IN VPC: gets ENI in specified subnets. No internet access by default
  • Lambda in VPC + internet needed → deploy Lambda in private subnet + NAT Gateway in public subnet
  • Trap: Lambda in VPC in a public subnet does NOT get internet — it doesn't get a public IP. Must use NAT in a separate public subnet.
  • Lambda in VPC accessing AWS services: use VPC Endpoints (no internet needed) or NAT Gateway

⚖️ ALB + Lambda

  • ALB can invoke Lambda as a target group target
  • Multi-value headers: when enabled, query string params with same key become arrays in the event object
  • Lambda response format must include: statusCode, headers, body, optional isBase64Encoded
  • ALB performs HTTP ↔ JSON conversion (request to JSON event, JSON response to HTTP)
  • Health checks: ALB can health-check the Lambda function

📚 Layers & Extensions

  • Layers: reusable code/libraries packaged as ZIP, up to 5 layers per function
  • Layers count toward the 250 MB unzipped deployment limit
  • Use case: share common dependencies (SDKs, libraries) across multiple functions
  • Extensions: integrate monitoring, security, governance tools (run as companion processes)
  • Internal extensions: run in the same process. External extensions: run as separate processes.

📨 Event Source Mapping Details

  • Kinesis / DynamoDB Streams: Lambda polls shards, processes in order per shard, supports batch window, bisect on error, max retry attempts, parallelization factor (up to 10 per shard)
  • SQS: Lambda polls queue, batch size 1–10 (standard) or up to 10,000 (with batch window). Uses long polling.
  • SQS FIFO: Lambda scales to number of active message groups
  • SQS standard: Lambda scales up to 1,000 batches of concurrent functions (up to 60 more per minute)
  • Key: On failure with event source mapping → records return to source (no DLQ on Lambda side). Use SQS DLQ on the source queue or a Lambda Destination for failures.

⚠️ Gotchas & Exam Tips

  • Trap 15-minute timeout — if task takes longer, use Step Functions, ECS, or Batch instead
  • Trap "Eliminate cold starts" = Provisioned Concurrency (NOT reserved concurrency)
  • Trap Reserved concurrency set to 0 = function is disabled (throttled to 0)
  • Trap DLQ is for async invocations only. For event source mapping (SQS/Kinesis/DDB), configure DLQ on the source or use Destinations
  • Trap Destinations are recommended over DLQ — they capture both success and failure with full context
  • Trap Lambda in VPC + needs DynamoDB access → use VPC Gateway Endpoint for DynamoDB (free, no NAT needed)
  • Remember "Simple URL rewrite/redirect at edge" = CloudFront Functions. "Complex logic at edge accessing AWS" = Lambda@Edge
  • Remember Lambda function URL: built-in HTTPS endpoint (no API Gateway needed), supports IAM auth or no auth
  • Remember X-Ray tracing: enable Active Tracing in Lambda config, SDK auto-instrumented, no daemon needed (Lambda manages it)
  • Trap /tmp is ephemeral per execution environment — data persists across warm invocations of the same instance but is NOT guaranteed
  • Trap Env var 4 KB limit — for larger config, use SSM Parameter Store or Secrets Manager and fetch at init

🗄️ DynamoDB & DAX

🔑 Core Concepts

  • DynamoDB: fully managed NoSQL, key-value + document database, serverless, single-digit ms latency
  • Max item size: 400 KB
  • Primary key options:
    • Partition Key only (simple): must be unique per item
    • Partition Key + Sort Key (composite): combination must be unique; same PK can have multiple items with different SKs
  • Supported data types: String, Number, Binary, Boolean, Null, List, Map, String Set, Number Set, Binary Set
  • TTL: auto-delete expired items at no extra cost. Items may remain up to 48 hours after expiration before deletion. Expired items still appear in queries/scans until actually deleted.
  • PartiQL: SQL-compatible query language for DynamoDB (SELECT, INSERT, UPDATE, DELETE)

📐 RCU / WCU Calculations

  • 1 WCU = 1 write per second for an item up to 1 KB. Item >1 KB → round up (e.g., 2.5 KB item = 3 WCU)
  • 1 RCU = 1 strongly consistent read per second for an item up to 4 KB
  • 1 RCU = 2 eventually consistent reads per second for an item up to 4 KB
  • Transactional reads/writes consume 2x the capacity (1 transactional write of 1 KB = 2 WCU)
  • Example: 10 strongly consistent reads/sec of 6 KB items = 10 × ceil(6/4) = 10 × 2 = 20 RCU
  • Example: 10 eventually consistent reads/sec of 6 KB items = (10 × 2) / 2 = 10 RCU
  • Example: 5 writes/sec of 4.5 KB items = 5 × ceil(4.5/1) = 5 × 5 = 25 WCU

🔄 DynamoDB Streams

  • Ordered stream of item-level modifications (insert, update, delete)
  • Retention: 24 hours
  • Stream records contain: KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, or NEW_AND_OLD_IMAGES
  • Can trigger Lambda functions (event source mapping)
  • Use cases: cross-region replication (Global Tables require it), real-time analytics, send notifications on changes
  • Kinesis Data Streams for DynamoDB: alternative to DynamoDB Streams with longer retention (up to 365 days) and higher throughput

⚡ DAX (DynamoDB Accelerator)

  • In-memory cache for DynamoDB — microsecond latency for cached reads
  • No application code change needed (API-compatible with DynamoDB)
  • Default TTL: 5 minutes (item cache), 5 minutes (query cache)
  • Multi-AZ (3 nodes minimum recommended for production)
  • Solves hot partition / hot key problem
  • Critical DAX is NOT suitable for strongly consistent reads — DAX only supports eventually consistent reads
  • Key DAX vs ElastiCache: DAX = individual item/query cache for DynamoDB. ElastiCache = aggregation/computation results store, general-purpose cache

🌍 Global Tables

  • Multi-region, multi-active (read/write in any region)
  • Requires DynamoDB Streams enabled
  • Replication is eventually consistent across regions (typically sub-second)
  • Use cases: disaster recovery, low-latency global access, active-active
  • Last writer wins conflict resolution

🔧 Operations & API

  • Query: by partition key (required) + optional sort key condition — efficient, returns sorted results
  • Scan: reads entire table — expensive, consumes lots of RCU. Use parallel scan for speed, Limit parameter, or FilterExpression (applied AFTER read, still consumes full RCU)
  • BatchWriteItem: up to 25 PutItem/DeleteItem in one call (max 16 MB)
  • BatchGetItem: up to 100 items (max 16 MB)
  • TransactWriteItems / TransactGetItems: ACID transactions, up to 100 actions, all-or-nothing
  • Conditional writes: PutItem/UpdateItem/DeleteItem with ConditionExpression — idempotent, prevents overwriting
  • ProjectionExpression: return only specified attributes (reduces data transfer)

⚠️ Gotchas & Exam Tips

  • Trap FilterExpression on Scan/Query does NOT reduce RCU consumption — filtering happens after data is read
  • Trap 400 KB max item size — for larger objects, store in S3 and keep S3 URL in DynamoDB
  • Trap GSI eventually consistent ONLY — if question requires strong consistency on an alternate key, it cannot use GSI
  • Trap TTL does NOT delete immediately — up to 48 hours delay. If you need instant deletion, call DeleteItem
  • Trap "ProvisionedThroughputExceededException" → solutions: exponential backoff, DAX for reads, increase capacity, better partition key design
  • Trap DAX cannot help with write-heavy workloads — it only caches reads
  • Key "Serverless NoSQL with single-digit ms" = DynamoDB
  • Key "Hot partition" → use DAX or redesign partition key (add random suffix)
  • Key "Multi-region active-active database" = DynamoDB Global Tables
  • Remember WCU/RCU calculations appear frequently — practice ceiling division for item sizes
  • Remember Batch operations return UnprocessedItems/UnprocessedKeys — must retry with exponential backoff

📊 CloudWatch, CloudTrail & Config

🔑 CloudWatch Metrics

  • Default monitoring: every 5 minutes (free)
  • Detailed monitoring: every 1 minute (extra cost)
  • Custom metrics: Standard resolution = 1 min, High resolution = 1 sec (StorageResolution API parameter)
  • Metric data retention:
    • Period <60 sec → retained 3 hours
    • Period 60 sec → retained 15 days
    • Period 300 sec (5 min) → retained 63 days
    • Period 3600 sec (1 hr) → retained 455 days (15 months)
  • Critical EC2 default metrics do NOT include: memory utilization, disk space, swap usage — need CloudWatch Agent
  • Default EC2 metrics: CPU, network in/out, disk read/write (ops + bytes), status checks

🚨 CloudWatch Alarms

  • Three states: OK, ALARM, INSUFFICIENT_DATA
  • Evaluation period: how many data points to evaluate
  • Actions on ALARM:
    • EC2: stop, terminate, reboot, recover
    • Auto Scaling: scale out/in
    • SNS: send notification (email, Lambda, HTTP, SQS)
  • Composite Alarms: combine multiple alarms with AND/OR logic — reduces alarm noise
  • EC2 instance recovery: same private IP, public IP, EIP, metadata, placement group. Only works with EBS-backed instances

📝 CloudWatch Logs

  • Hierarchy: Log Groups → Log Streams
  • Retention: configurable from 1 day to 10 years, or never expire
  • Export to S3: batch export (up to 12 hours delay). For real-time → use Subscriptions
  • Metric Filters: parse log data → extract custom metrics (e.g., count errors, extract latency values)
  • Subscription Filters: real-time streaming to Lambda, Kinesis Data Streams, Kinesis Data Firehose
  • CloudWatch Logs Insights: interactive query language for searching/analyzing logs
  • Cross-account log subscriptions: aggregate logs from multiple accounts

🔬 X-Ray

  • Distributed tracing: visualize request flow across microservices
  • Requires: X-Ray SDK in application code + X-Ray Daemon on compute
  • Key concepts:
    • Segments: data from a service
    • Subsegments: granular detail (AWS calls, HTTP calls, SQL queries)
    • Traces: end-to-end request across services
    • Annotations: key-value pairs, indexed, used for filtering traces
    • Metadata: key-value pairs, NOT indexed, additional data storage
  • Default sampling: 1 request/sec + 5% additional (can customize)
  • Lambda: managed integration — enable Active Tracing, no daemon needed (AWS runs it)
  • EC2/ECS: must install and run X-Ray Daemon (sidecar in ECS)
  • Elastic Beanstalk: built-in X-Ray support via .ebextensions config
  • API Gateway: enable X-Ray tracing in stage settings

📡 EventBridge (formerly CloudWatch Events)

  • Event-driven serverless event bus
  • Event buses:
    • Default: receives events from AWS services
    • Custom: for your own application events
    • Partner: SaaS integrations (Datadog, Auth0, Zendesk, etc.)
  • Rules: match event patterns → route to targets (Lambda, SQS, SNS, Step Functions, etc.)
  • Schedule rules: cron or rate expressions (e.g., "every 5 minutes")
  • Schema Registry: infer schemas from events, generate code bindings
  • Archive & Replay: store events and replay them later (great for debugging)
  • Can aggregate events from multiple accounts into a central event bus

🔍 CloudTrail

  • Records ALL API calls made in your AWS account — who, when, what, from where
  • Enabled by default — Event History retains 90 days of management events (free)
  • For longer retention: create a Trail → deliver to S3 bucket (optionally + CloudWatch Logs)
  • Event types:
    • Management Events: operations on AWS resources (CreateVPC, AttachRole) — logged by default
    • Data Events: operations on data (S3 GetObject, Lambda Invoke) — extra cost, disabled by default
    • Insights Events: detect unusual API activity patterns — extra cost
  • Multi-region trail: single trail covers all regions
  • Key CloudTrail is NOT real-time — events delivered within ~15 minutes
  • For real-time monitoring of API calls: CloudTrail → CloudWatch Logs → Metric Filter → Alarm
  • S3 delivery: can enable SSE-S3 or SSE-KMS encryption, log file integrity validation

⚙️ AWS Config

  • Records configuration changes over time — answers "What did my resource look like last Tuesday?"
  • Key Config does NOT prevent changes — it records, evaluates, and alerts
  • Config Rules: AWS managed (75+ predefined) or custom (Lambda-based)
  • Evaluations: triggered on config change or on a schedule
  • Remediation: auto-remediate via SSM Automation documents (e.g., auto-enable encryption)
  • Config Aggregator: collect Config data across multiple accounts and regions (multi-account, multi-region view)
  • Compliance timeline: visual history of resource compliance over time
  • Use cases: "Is encryption enabled on all S3 buckets?", "Were any security groups ever open to 0.0.0.0/0?", "Are all EC2 instances of approved type?"

🌐 VPC & Networking

🔑 VPC Fundamentals

  • Max 5 VPCs per region (soft limit, can increase)
  • Max 5 CIDRs per VPC (min /28, max /16)
  • Default VPC: created automatically, one public subnet per AZ with /20 CIDR, has IGW, default SG, default NACL
  • VPC CIDR cannot overlap with other VPCs you want to peer with
  • Tenancy: default (shared hardware) or dedicated (single-tenant hardware)

🏗️ Subnets

  • Public subnet: route table has route to Internet Gateway (IGW)
  • Private subnet: no direct route to IGW
  • Reserved IPs per subnet: 5 addresses
    • .0 = Network address
    • .1 = VPC router
    • .2 = DNS
    • .3 = Future use
    • Last IP = Broadcast
  • /24 CIDR = 256 - 5 = 251 usable IPs
  • A subnet lives in exactly one AZ

🚪 Internet Gateway & NAT

  • IGW: one per VPC, enables internet access for instances with public IPs in public subnets
  • For an instance to reach internet: IGW + route in route table + public IP (or EIP)

Security GroupsCannot attachCan attach
BastionCannot use as bastionCan use as bastion

  • HA pattern: deploy one NAT Gateway per AZ in each public subnet for cross-AZ resilience
  • Egress-Only IGW: like NAT Gateway but for IPv6 — allows outbound IPv6, blocks inbound IPv6 from internet

🔗 VPC Peering

  • 1:1 private connection between two VPCs using AWS network
  • Critical NOT transitive: A↔B and B↔C does NOT mean A↔C
  • CIDRs must NOT overlap
  • Works cross-account and cross-region
  • Must update route tables in both VPCs
  • Security groups can reference peered VPC's SGs (same region only)

🌟 Transit Gateway

  • Hub-and-spoke model: connect thousands of VPCs and on-premises networks
  • Transitive routing: A↔TGW↔B means A can reach B (unlike VPC Peering)
  • Works across accounts and regions (via TGW Peering)
  • Attachments: VPCs, VPN connections, Direct Connect Gateways, TGW Peering, Connect (SD-WAN)
  • Supports IP Multicast (only AWS service that does)
  • Route tables for fine-grained routing control between attachments
  • Use case: complex network topology with many VPCs needing interconnection

🔐 VPN & Direct Connect

  • Site-to-Site VPN:
    • Customer Gateway (CGW): on-premises side (software or hardware appliance)
    • Virtual Private Gateway (VGW): AWS side (attach to VPC)
    • Encrypted over public internet, max 1.25 Gbps per tunnel
    • Quick to set up (minutes to hours)
  • VPN CloudHub: multiple customer sites connect through same VGW — hub-and-spoke over VPN. Sites can communicate with each other through AWS.

  • DX Gateway: connect to multiple VPCs in different regions using a single DX connection

📊 Flow Logs

  • Capture IP traffic info at VPC, Subnet, or ENI level
  • Log accepted, rejected, or all traffic
  • Destinations: S3, CloudWatch Logs, Kinesis Data Firehose
  • Traffic NOT captured:
    • Traffic to/from 169.254.169.254 (instance metadata)
    • DHCP traffic
    • DNS traffic to Amazon-provided DNS (Route 53 Resolver)
    • Windows license activation traffic
    • Traffic to reserved IP of VPC router

🏰 Bastion Host & Traffic Mirroring

  • Bastion Host: EC2 instance in public subnet — SSH/RDP gateway to private instances
  • HA pattern: 2 bastions in 2 AZs behind NLB (not ALB — SSH is TCP, not HTTP)
  • Security group: allow SSH (port 22) from your IP only on bastion; private instances allow SSH only from bastion SG
  • Modern alternative: SSM Session Manager — no bastion needed, no port 22 open, audit trail via CloudTrail
  • VPC Traffic Mirroring: copy network traffic from ENIs for deep packet inspection, send to NLB or single EC2 (IDS/IPS use case)

⚠️ Gotchas & Exam Tips

  • Trap VPC Peering is NOT transitive — for transitive routing, use Transit Gateway
  • Trap Gateway Endpoints are free and support S3 + DynamoDB only. Interface Endpoints cost money but support everything else.
  • Trap NACLs are stateless — if you allow inbound port 80, you MUST also allow outbound ephemeral ports (1024-65535) for the response
  • Trap DX takes >1 month. "Need connectivity today" = VPN. "Need consistent low latency" = DX
  • Trap DX is NOT encrypted by default. DX + VPN = encrypted private link
  • Trap NAT Gateway is HA within one AZ only — deploy one per AZ for full HA
  • Trap Egress-Only IGW is for IPv6 ONLY (IPv6 has no NAT — all addresses are public). For IPv4, use NAT Gateway.
  • Key "Connect 100+ VPCs" = Transit Gateway
  • Key "Access S3 privately from VPC" = VPC Gateway Endpoint
  • Key "Expose service in your VPC to other VPCs privately" = PrivateLink (Interface Endpoint)
  • Key "IP Multicast" = Transit Gateway (only option)
  • Key "Block specific IP" = NACL (deny rule). Security Groups can only allow, not deny.
  • Key "SSH to private instances without bastion" = SSM Session Manager
  • Remember /24 = 251 usable IPs, /28 (smallest) = 11 usable IPs, /16 (largest) = 65,531 usable IPs
  • Remember VPN CloudHub = connect multiple branch offices through AWS VPN (hub-and-spoke, encrypted, over internet)

🔑 AWS Backup & DMS

  • AWS Backup: centralized backup for RDS/DynamoDB/EFS/EC2/FSx/S3/Aurora. Cross-region + cross-account. Backup Vault Lock: WORM, even root cannot delete
  • DMS: source DB stays available. Homogeneous = direct. Heterogeneous = needs SCT (Schema Conversion Tool). CDC = continuous replication

🔑 Snow Family, DataSync & Storage Gateway

  • Snowcone: 8-14TB | Snowball Edge: 80-210TB | Snowmobile: 100PB
  • Use Snow when network transfer takes >1 week
  • Snowball CANNOT import directly to Glacier — S3 → lifecycle → Glacier
  • DataSync: online transfer up to 10Gbps. Agent required on-prem. Targets: S3/EFS/FSx. = migration tool
  • Storage Gateway = ongoing hybrid access. S3 File GW (NFS/SMB→S3), Volume GW (iSCSI), Tape GW, FSx File GW
  • Transfer Family: managed FTP/FTPS/SFTP into S3 or EFS
  • MGN (Application Migration Service): lift-and-shift. Replaces legacy SMS

⚠️ Exam Tips & Gotchas

  • "Cheapest DR" → Backup & Restore
  • "Near-zero downtime" → Multi-Site Active-Active
  • "Core systems running, scale up on disaster" → Pilot Light
  • "Reduced copy, scale out on disaster" → Warm Standby
  • Volume GW Cached = S3 primary + local cache. Stored = local primary + S3 backup
  • DataSync = migration/transfer. Storage Gateway = ongoing hybrid access
  • DMS + SCT only for heterogeneous migrations
